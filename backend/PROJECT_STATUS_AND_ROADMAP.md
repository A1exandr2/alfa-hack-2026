# Smart Credit Cabinet — статус и план проекта

## Цель

Сделать демонстрационный цифровой кредитный кабинет для представителя малого бизнеса: регистрация → привязка компании → просмотр данных → выбор продукта → заявка → проверки и обогащение → оценка риска → решение → предложение → подтверждение.

Система строится как модульный монолит: Frontend обращается к FastAPI, Backend хранит состояние в PostgreSQL. Источники внешних данных подключаются через интерфейсы провайдеров и заменяемые адаптеры. Все текущие провайдеры и продукты помечены `DEMO`; это синтетические данные, не сведения реальных компаний или БКИ.

В `dev` DevOps подключил ML-фасад внутри Backend и отдельный runtime Ollama/Qwen через общий Compose. Backend отвечает за API-контракт, данные компании и окончательные бизнес-правила; демонстрационный ML-score не заменяет решение по заявке.

## Что уже сделано

### Инфраструктура

- Docker Compose запускает PostgreSQL, миграции, FastAPI, Nginx и Ollama (`make up` / `make up-gpu`).
- Секреты хранятся в локальном `.env`; `make init` генерирует секреты, а `.env.example` не содержит их значений.
- Есть Makefile-команды для запуска, остановки, тестирования, smoke-проверки и статуса.
- CI включает проверки кода и контейнерной сборки.
- Frontend пока не реализован; сейчас Nginx направляет корневую страницу в Swagger UI.

### Backend и API

Авторизация:

- `POST /api/v1/auth/register` — создаёт пользователя без компании и возвращает JWT.
- `POST /api/v1/auth/login` — проверяет пароль и выдаёт JWT.
- `GET /api/v1/auth/me` — возвращает текущего пользователя.
- Пароли хешируются `scrypt`; защищённые маршруты используют Bearer JWT.

Компания:

- `POST /api/v1/company/link` — привязывает компанию по ИНН.
- `GET /api/v1/company` — возвращает компанию пользователя.
- `CompanyProvider` отделяет интеграцию от бизнес-логики; сейчас используется `DemoCompanyProvider`.

Финансы:

- `GET /api/v1/company/financials` — при первом запросе загружает и сохраняет demo-данные.
- `PATCH /api/v1/company/financials` — частично обновляет показатели; проверяет диапазоны и выставляет источник `USER_VERIFIED`.
- Хранятся выручка, прибыль, расходы, число сотрудников и долг; отрицательная прибыль разрешена.
- Данные поступают через `FinancialProvider`; текущие значения синтетические.

Кредитная история:

- `GET /api/v1/company/credit-history` — возвращает агрегат через `CreditHistoryProvider` и сохраняет его.
- Текущий provider синтетический; реальные данные БКИ не подключены.

Кредитные продукты:

- `GET /api/v1/credit-products` — список активных продуктов.
- `GET /api/v1/credit-products/{product_id}` — карточка продукта.
- В БД заведены три demo-продукта с диапазонами суммы, срока и ставки. Условия не являются банковскими предложениями.

Схема PostgreSQL управляется Alembic; текущий head — `0008_application_snapshot_audit`. Тесты запускаются командой `make test` с отдельной временной PostgreSQL.

### ML и скоринг в dev

- `POST /api/v1/company/score`: JWT, компания текущего пользователя, расчёт признаков из БД, скоринг по правилам и объяснение Qwen 3.5 4B.
- Fallback-рекомендации при сбое модели, явный источник `AI` / `Fallback_Rules`.
- Генератор четырёх CSV по 500 синтетических записей; автоматического импорта в БД нет.
- Проверены 27 тестов, сквозной запрос к Qwen на GPU и CI. Детали: [ML](../docs/ml.md).

## Ограничения текущей версии

- Нет пользовательского интерфейса Frontend.
- Данные компании, финансов и кредитной истории синтетические; demo-показатели сейчас одинаковы для разных ИНН.
- Реальных интеграций с DaData, Контуром, БКИ и банковскими системами нет. К реальным данным БКИ можно переходить только при наличии прав и разрешений.
- Каталог продуктов фиксируется миграцией; управление каталогом через UI/API пока не предусмотрено.
- Реализованы заявки, история статусов, snapshot версии 2 и аудит; submit вызывает ML-фасад и сохраняет `risk_score`, `risk_level`, факторы, `ai_advice` и источник AI/fallback.
- Ещё нет Backend-сущностей/правил финального решения, предложений и новостей. ML-поле `decision` намеренно игнорируется. Каталог продуктов из БД не передаётся Qwen; качество рекомендаций требует доработки.

## План до MVP

### 1. Заявки — Backend

- Готово: `Application` со связями пользователя, компании и кредитного продукта; сумма, срок и цель.
- Готово: создание черновика, список, просмотр и редактирование до отправки.
- Готово: валидация суммы и срока по выбранному продукту.
- Готово: отправка заявки и переходы до `SCORING`:

  `DRAFT → SUBMITTED → DATA_CHECK → DATA_ENRICHMENT → SCORING → DECISION → OFFER → COMPLETED`

- Вынести смену статусов в сервис с проверкой допустимых переходов; не менять статус напрямую через произвольный PATCH.

### 2. Проверки, снимки и аудит — Backend

- Готово: при отправке получать недостающие финансы и кредитную историю через provider-интерфейсы.
- Готово: сохранять snapshot входных данных и скоринговой оценки; изменение профиля не переписывает прошлый snapshot.
- Готово: история статусов и Audit Log с событием, временем и участником/сервисом.

### 3. Оценка и решение — совместно с DevOps

- Готово: связать отправку заявки и snapshot с `ml.facade.score_and_explain`; runtime модели запускается DevOps через Compose.
- Далее: подключить каталог продуктов и срок заявки к бизнес-правилам Backend; они пока не являются входом численного ML-score.
- Далее: Backend применяет детерминированные правила к score и snapshot, учитывая продукт, финансовые данные, кредитную историю, сумму и срок.
- Далее: сохранять результат `APPROVED`, `CONDITIONAL_APPROVAL`, `NEED_MORE_DATA` или `REJECTED`; ML score сам по себе не является решением.
- Готово: при сбое Ollama фасад возвращает оценку по правилам и источник `Fallback_Rules`; финальное решение по заявке остаётся Backend.

### 4. Предложение и завершение заявки — Backend

- При одобрении создать `Offer`: одобренная сумма, срок, ставка, ежемесячный и общий платёж.
- Добавить получение решения и предложения, подтверждение предложения и симуляцию завершения/выдачи в рамках MVP.
- Каждое действие отражать в истории заявки и аудите.

### 5. Новости и Frontend

- Добавить `GET /api/v1/news` с demo-новостями, отфильтрованными по данным компании; явно показывать, что лента демонстрационная.
- Frontend реализует регистрацию/вход, onboarding и привязку ИНН, Dashboard, компанию, финансы, кредитную историю, каталог продуктов, создание заявки, статусы, решение, предложение и новости.
- UI отображает состояние, возвращённое Backend; бизнес-решения на клиенте не принимать.

### 6. Интеграция и демонстрация командой

- Data Engineer готовит синтетические профили с низким, средним и высоким риском для воспроизводимых сценариев; не использовать реальные кредитные данные.
- QA проверяет сквозные сценарии: одобрение, изменение условий, запрос дополнительных данных и отказ; тестирует проверки доступа, валидацию, повторные запросы и сбои провайдеров.
- DevOps добавляет Frontend в существующий общий Compose с Backend и Ollama, поддерживает CI и smoke-проверки.
- Подготовить README/runbook, OpenAPI, ER-диаграмму, схему архитектуры, диаграмму состояний, API collection, синтетические fixtures и `THIRD_PARTY_NOTICES`.

## Критерий готовности MVP

Пользователь может пройти один работающий сценарий от регистрации до подтверждения предложения; данные сохраняются в PostgreSQL, заявка и решение воспроизводимы по snapshot’ам, переходы статусов и решения попадают в аудит, а демонстрационный запуск выполняется через Docker Compose. Синтетические данные и границы интеграций явно обозначены.
