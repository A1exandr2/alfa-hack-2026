# ML + Backend в dev

Ветка `dev` создана от `ml`, затем в неё объединена `backend`. Исходные ветки не удаляются.

## Что сделал ML-инженер

- `ml/risk_scoring.py`: прозрачный скоринг по правилам (0–100; выше — риск выше), уровень риска и APPROVED / MANUAL_REVIEW. Это не обученная модель предсказания дефолта.
- `ml/llm_assistant`: системный промпт, ограниченная очистка запроса, JSON Schema через Pydantic, вызов Qwen `qwen3.5:4b` через Ollama с отключённым thinking.
- Запасные рекомендации по правилам при сбое или невалидном JSON модели.
- `ml/facade.py`: единая функция `score_and_explain` для Backend.
- `data/generate_data.py`: генератор 500 синтетических компаний, финансовых профилей, кредитных историй и заявок в четыре CSV с распределением рисков; использует Faker. Эти CSV автоматически не импортируются в PostgreSQL. Обученных весов в Git нет.

Изначально Ollama не запускалась через Compose, Backend не импортировал ML, а Dockerfile ML был пустым. В `dev` добавлены runtime Ollama, вызов фасада из API, настройки адреса/модели/таймаута, ограничение контекста 4096 и объединённые тесты. Конфликт версий Pydantic устранён: используется lock Backend.

## Единый запуск

```bash
make up-gpu        # NVIDIA + установленный NVIDIA Container Toolkit
# или make up     # CPU, медленнее
make check         # API/auth/БД через Nginx
make check-ml      # реальный запрос к Qwen, требует source=AI
make test          # тесты в отдельной БД, включая fallback; без загрузки модели
make logs SERVICE=ollama
make down          # сохранить модель и БД
```

Первый запуск скачивает несколько ГБ весов. Модель хранится в `credit_ollama_data`, не в Git или образе Backend. `OLLAMA_MODEL` и `OLLAMA_TIMEOUT` задаются в `.env` (по умолчанию qwen3.5:4b и 120 секунд). После смены модели повторите `make up-gpu` или `make up`. Одновременно загружена одна модель и обслуживается одна генерация Ollama.

Общий Dockerfile — `backend/Dockerfile`: ML работает внутри модульного монолита. Отдельного Python ML-сервиса и дублирующих Makefile/Compose нет; пустой `ml/Dockerfile` не используется. Ollama использует готовый образ, закреплённый digest. `docker-compose.gpu.yml` добавляет только GPU, основная конфигурация общая. `.dockerignore` исключает секреты, локальные окружения и ML-артефакты.

`make up-core` запускает только API/БД/Nginx и не выключает уже запущенную Ollama. Если Ollama отсутствует, рекомендации возвращаются через fallback. CI использует up-core и тесты без скачивания LLM; настоящую генерацию проверяют отдельно командой check-ml.

## Контракт

Swagger: http://localhost:8080/docs. Зарегистрируйтесь, авторизуйтесь Bearer JWT и привяжите компанию через `/api/v1/company/link`, затем:

```http
POST /api/v1/company/score
Authorization: Bearer <token>
Content-Type: application/json

{"loan_amount":1000000,"user_query":"Нужен кредит на оборудование"}
```

Endpoint берёт только компанию текущего пользователя. При отсутствии финансов и кредитной истории загружаются существующие demo provider данные и сохраняются в БД. Признаки:

- company_age = (сегодня − registration_date) / 365.25;
- profit_margin = profit_annual / revenue_annual;
- debt_load = current_debt / revenue_annual (запрашиваемая сумма не прибавляется: это исходная формула ML);
- has_overdue = overdue_count > 0 или overdue_amount > 0.

Новые demo-компании получают явно синтетическую дату регистрации 2019-01-01 от DemoCompanyProvider. Старые записи с пустой датой автоматически не меняются; для smoke создаётся новая demo-компания.

Без компании — 404; отсутствующая/будущая дата регистрации или выручка <= 0 — 422, без выдуманных признаков. Сумма положительная, запрос до 500 символов. Синхронная генерация вынесена из async event loop в thread pool.

Ответ содержит `risk_score`, `risk_level`, `decision`, `top_factors` и `ai_advice` с `source: AI | Fallback_Rules` и полями `recommended_product`, `explanation`, `top_risk_factors`, `next_step`. Падение Ollama не изменяет численный скоринг. Источник обязательно проверять: успешный HTTP 200 сам по себе не доказывает работу LLM.

## Ограничения текущего прототипа

Данные провайдеров и условия каталога синтетические. ML выбирает одно из трёх названий продуктов, не привязывая их к ID/ставкам каталога, не учитывает доступность лимитов, не создаёт заявку и не сохраняет результат скоринга. Факторы и рекомендации требуют проверки: запасные правила могут перечислять оба фактора (просрочки и нагрузку), даже когда сработал только один. Очистка строк не гарантирует защиту от prompt injection. Проверяется схема JSON, но достоверность и качество рекомендации не гарантируются. APPROVED здесь — результат демонстрационной формулы, не выданный кредит.

## Проверки dev (22.10.2026)

27 pytest-тестов прошли на отдельной PostgreSQL; проверены штатный скоринг, fallback при недоступной Ollama/невалидном JSON, очистка запроса, JWT и преобразование финансовых признаков. Генератор запущен в одноразовом контейнере: четыре CSV по 500 строк. Gitleaks, Semgrep (210 правил) и Trivy зависимостей: находок нет. Проверены health/readiness, Swagger и auth через Nginx.

Реальный `make check-ml` прошёл через Nginx → JWT API → ML facade → Ollama: source=AI, risk_score=25, Low, APPROVED. Ollama 0.32.6 показывает qwen3.5:4b, 100% GPU, контекст 4096; первый запрос с загрузкой и прогревом занял около 62 секунд. Все четыре постоянных сервиса healthy. Модель предложила «Оборотный» для покупки оборудования и превысила требование двух предложений: это проверка работоспособности интеграции, а не подтверждение качества кредитной рекомендации.

После прогрева проверены ещё два вызова фасада с source=AI: молодая компания — score=60 / APPROVED / Оборотный за 2,9 секунды; просрочки + высокая нагрузка + отрицательная прибыль — score=90 / MANUAL_REVIEW / Оборотный за 3,4 секунды.
