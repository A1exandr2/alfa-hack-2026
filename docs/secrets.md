# Секреты: SOPS + age

`.env` — локальный незашифрованный файл с правами 0600, исключён из Git и Docker build context. `.env.example` содержит только имена параметров с пустыми значениями. Для нового изолированного окружения `python3 devops/scripts/init-env.py --fresh-local` генерирует случайные пароли и локальные настройки; существующий `.env` не перезаписывается.

`secrets/server.enc.env` — зашифрованный dotenv-файл для переноса на сервер и хранения в Git. `.sops.yaml` содержит только публичный age recipient. Приватная identity находится в `.local/secrets/age/keys.txt` (0600, родительский каталог 0700) и никогда не коммитится. Ключ нельзя восстановить из зашифрованного файла: сохраните отдельную защищённую резервную копию.

Инструменты уже установлены на текущем компьютере: SOPS 3.9.4 и age 1.2.1. На новом хосте установите их из официальных дистрибутивов: [SOPS](https://github.com/getsops/sops/releases), [age](https://github.com/FiloSottile/age/releases). Использование ENV и age поддерживается [документацией SOPS](https://getsops.io/docs/).

## Ежедневная работа

```sh
# Выполняется один раз в новом проекте, не заменяет существующую identity:
make secrets-key

# После изменения локального .env:
make secrets-encrypt
make secrets-check

# Только если локального .env ещё нет:
make secrets-decrypt
```

`secrets-encrypt` использует публичный recipient из `.sops.yaml`; приватный ключ для шифрования не требуется. `secrets-check` проверяет расшифровку и MAC, а при наличии `.env` — соответствие всех значений. Команды не печатают расшифрованные значения. Расшифровка по умолчанию не заменяет существующий `.env`; намеренная замена выполняется `python3 devops/scripts/sops-env.py decrypt --force`.

В Git нужны `.sops.yaml`, `secrets/server.enc.env`, пустой `.env.example` и код инструментов. Приватную identity и `.env` передавайте отдельно от репозитория. Не передавайте пароль, JWT или ключ в аргументах shell-команд и не публикуйте вывод `docker compose config` без `--quiet`.

## Добавление и изменение секрета одной командой

```sh
make secret-set NAME=DADATA_API_KEY
# Или без NAME: команда спросит имя и затем значение.
make secret-set
```

Значение вводится скрыто, не передаётся в аргументах команды и не попадает в shell history. Команда сначала расшифровывает текущий файл и проверяет отсутствие несохранённых изменений в локальном `.env`, затем сохраняет обновлённый ciphertext атомарно. Если локальный `.env` уже существует, обновляется и он; на сервере без `.env` файл не создаётся. В `.env.example` добавляется только пустое имя нового параметра. Значения со знаками `$`, кавычками и обратными слешами передаются в Compose буквально.

Для автоматизации предусмотрен `make secret-set-stdin NAME=VARIABLE`: значение поступает через stdin из другого защищённого источника. Не подставляйте секрет прямо в текст shell-команды. Многострочные значения не поддерживаются; сертификаты и файлы ключей следует хранить отдельными зашифрованными файлами.

Сохранение конфигурации не изменяет пароль роли внутри существующей PostgreSQL и не сбрасывает пароль уже созданного администратора. Для этих паролей нужна согласованная ротация. Новый `JWT_SECRET` завершит текущие сессии после применения конфигурации.

Новые имена автоматически сохраняются и шифруются, но новая интеграция должна читать соответствующие настройки. Получатели существующих параметров явно перечислены в `docker-compose.yml`: ключ DaData поступает в backend, пароль PostgreSQL — в PostgreSQL и строку подключения, пароль начального администратора — только в одноразовый bootstrap-контейнер. Произвольные секреты не передаются во все контейнеры.

## Автоматический серверный режим без .env

Серверный launcher `devops/scripts/server-runtime.py` расшифровывает SOPS в памяти и предоставляет Compose явный env-file через Linux memfd (`/proc/<pid>/fd/<fd>`). Открытый `.env` не читается и не создаётся. При неверном ключе или нарушенной целостности Docker-команды не выполняются. Уже экспортированные настройки с теми же именами удаляются из окружения дочернего процесса, чтобы старый пароль в shell не перекрыл SOPS. Секреты передаются в окружение контейнеров согласно Compose; пользователь с доступом к Docker/root может их прочитать.

```sh
# Приватный ключ предоставляется один раз и остаётся вне репозитория:
export SOPS_AGE_KEY_FILE=/etc/credit/age/keys.txt
make server-check
make server-up
make server-status
make server-logs
make server-stop
```

По умолчанию включён режим CPU с Ollama и загрузкой модели. `CREDIT_DEPLOY_MODE=core` запускает API без локальной модели (резервные правила), `CREDIT_DEPLOY_MODE=gpu` подключает NVIDIA GPU. Режим GPU требует заранее настроенного NVIDIA Container Toolkit. Имя модели берётся из зашифрованных настроек. Все варианты сохраняют данные в Docker volumes.

Первый `server-up` автоматически создаёт Admin из зашифрованных `ADMIN_EMAIL`/`ADMIN_PASSWORD`; повторный запуск не меняет существующий пароль. Если почта уже принадлежит обычному пользователю, запуск не повышает его права и сообщает об ошибке. Для входа доступны `ADMIN_LOGIN` (Admin) и `ADMIN_EMAIL`. Остальные пользователи регистрируются сами.

## Перенос на новый сервер

Архив собирается `make server-package`, результат — `.local/deploy/credit-server.tar.gz` и SHA-256 рядом. Архив содержит код, Compose, systemd-шаблоны, публичную `.sops.yaml` и `secrets/server.enc.env`. Локальная база, `.env`, `.aws`, Git, приватные age-ключи и локальные артефакты исключены. Архив разворачивает новый экземпляр с пустой БД; перенос существующих данных — отдельное действие.

После передачи архива и отдельной передачи identity на сервер выполняется первоначальная настройка (команды ниже рассчитаны на root и каталог `/opt/credit/current`):

```sh
# Предварительно установите Docker Compose, Python 3, SOPS и age.
install -d -m 0755 /opt/credit/releases/bootstrap
# Архив уже находится на сервере, например /tmp/credit-server.tar.gz:
tar -xzf /tmp/credit-server.tar.gz -C /opt/credit/releases/bootstrap
ln -s /opt/credit/releases/bootstrap /opt/credit/current

install -d -m 0700 /etc/credit/age
# Передайте ключ отдельным защищённым каналом в /etc/credit/age/keys.txt.
chmod 0600 /etc/credit/age/keys.txt

install -m 0644 /opt/credit/current/devops/systemd/credit.service /etc/systemd/system/credit.service
systemctl daemon-reload
systemctl enable --now credit.service
```

Путь к identity уже указан в unit. SOPS находится в `/usr/local/bin/sops` либо `/usr/bin/sops`; PATH задан в unit. Режим можно поменять в `/etc/credit/runtime.conf`, например `CREDIT_DEPLOY_MODE=core`; этот файл не должен содержать сами пароли. `systemctl reload credit` повторно читает зашифрованные настройки и применяет их к Compose. После перезагрузки сервера служба запускается автоматически. Не нужно выполнять `make secrets-decrypt` или хранить серверный `.env`.

Для развёртывания через GitHub Actions вместо ручного bootstrap используйте [настройку CD](cd.md): она использует `/opt/credit/releases/<sha>`, current/previous и ежедневную очистку образов.

Веб-сервис по умолчанию слушает localhost:8080: внешний доступ предоставляется через reverse proxy с HTTPS. До переноса нужно определить домен, SSH-доступ и доступные ресурсы сервера. Новое значение порта/адреса сохраняется тем же `secret-set`; для deployment параметры можно редактировать на сервере, где уже есть identity.

### Автоматическое применение изменённого ciphertext (по желанию)

```sh
install -m 0644 /opt/credit/current/devops/systemd/credit-secrets.path /etc/systemd/system/credit-secrets.path
install -m 0644 /opt/credit/current/devops/systemd/credit-secrets-reload.service /etc/systemd/system/credit-secrets-reload.service
systemctl daemon-reload
systemctl enable --now credit-secrets.path
```

После изменения `secrets/server.enc.env` watcher запускает повторное применение. Для изменения только секрета достаточно `make secret-set NAME=...` на сервере либо доставки нового ciphertext. Автоматическое получение изменений из Git этим не настраивается. Во время обновления всего кода watcher следует остановить, завершить передачу файлов, вызвать `systemctl reload credit` и снова включить watcher: промежуточный checkout не должен запускаться.

Локальный ручной режим через `.env` и `make up-core` остаётся доступен для разработки. На сервере с уже существующим volume нельзя просто заменить пароль PostgreSQL в конфигурации: сначала меняется пароль роли в самой БД, затем синхронно обновляются настройки и контейнеры. Volume удалять не нужно.

## Ротация после утечки

На текущем локальном стеке заменены `POSTGRES_PASSWORD`, `JWT_SECRET` и пароль администратора; пароль роли изменён также в PostgreSQL. Исходные заявки и их снимки сохраняются. Файл восстановления старых настроек хранится зашифрованным в `.local/secrets/rotation/before.age`; это временный локальный материал, не часть поставки.

`DADATA_API_KEY` нельзя отозвать локальной генерацией случайной строки. Текущий ключ временно сохранён. После перевыпуска ключа в DaData вставьте новый в локальный `.env`, затем:

```sh
make secrets-encrypt
make secrets-check
docker compose --env-file .env up -d --force-recreate --no-deps backend
```

Если использовались внешние ключи других сервисов, их также нужно отозвать у поставщиков. Шифрование нового файла не удаляет значения из старых Git-коммитов; ротация лишает старые значения доступа. Переписывание истории — отдельная согласованная операция.

## Проверки

`python3 devops/scripts/test_secrets.py` проверяет шифрование/расшифровку, добавление секретов, запрет случайной перезаписи, отказ с чужим ключом и повреждённым MAC. `python3 devops/scripts/test_server_runtime.py` проверяет передачу через память, приоритет настроек, порядок запуска и отказ до обращения к Docker при ошибке SOPS. Полный серверный запуск и повторное создание Admin также проверены на отдельном временном Docker-проекте. CI создаёт изолированные настройки с `INIT_ENV_ARGS=--fresh-local`; production identity для тестов не нужна.
