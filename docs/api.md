# API-контракт

Документ описывает реализованный REST API ветки dev: системные endpoints, авторизацию, компанию, финансы, кредитную историю, каталог и скоринг.

## Общие правила

- Базовый префикс: `/api/v1`.
- Формат запросов и ответов: `application/json`.
- Идентификаторы сущностей: UUID в виде строки.
- Время: ISO 8601 в UTC.
- Защищённые endpoints используют заголовок:

```http
Authorization: Bearer <access_token>
```

Успешный ответ возвращает HTTP-код `2xx`. Ошибка возвращается в едином формате:

```json
{
  "detail": "Описание ошибки"
}
```

## Системные endpoints

### Проверка доступности backend

```http
GET /api/v1/health
```

Ответ `200 OK`:

```json
{
  "status": "ok",
  "service": "backend"
}
```

## Авторизация

### Регистрация тестового пользователя

```http
POST /api/v1/auth/register
Content-Type: application/json
```

Регистрация создаёт пользователя без компании. Привязка компании по ИНН выполняется отдельным запросом `POST /api/v1/company/link` после входа.

Запрос:

```json
{
  "email": "ivan@example.com",
  "password": "StrongPass123!",
  "full_name": "Иван Иванов"
}
```

Ответ `201 Created`:

```json
{
  "user": {
    "id": "00000000-0000-0000-0000-000000000010",
    "email": "ivan@example.com",
    "full_name": "Иван Иванов",
    "company_id": null
  },
  "access_token": "<jwt>",
  "token_type": "bearer"
}
```

Ошибки:

- `400 Bad Request` — некорректные данные;
- `409 Conflict` — пользователь с таким email уже существует;
- `422 Unprocessable Entity` — ошибка валидации данных запроса.

### Вход

```http
POST /api/v1/auth/login
Content-Type: application/json
```

Запрос:

```json
{
  "email": "ivan@example.com",
  "password": "StrongPass123!"
}
```

Ответ `200 OK` имеет тот же формат, что и успешная регистрация.

Ошибки:

- `401 Unauthorized` — неверный email или пароль;
- `422 Unprocessable Entity` — ошибка валидации запроса.

### Текущий пользователь

```http
GET /api/v1/auth/me
Authorization: Bearer ***
```

Ответ `200 OK`. До привязки компании поле `company_id` равно `null`; после привязки содержит UUID:

```json
{
  "id": "00000000-0000-0000-0000-000000000010",
  "email": "ivan@example.com",
  "full_name": "Иван Иванов",
  "company_id": null
}
```

Ошибки:

- `401 Unauthorized` — токен отсутствует, просрочен или недействителен;
- `404 Not Found` — пользователь из токена не найден.

## Компания

`POST /api/v1/company/link` привязывает компанию к текущему пользователю из JWT. Остальные endpoints раздела возвращают только данные связанной компании; передавать `company_id` в URL для MVP не требуется.

### Привязка компании

```http
POST /api/v1/company/link
Authorization: Bearer ***
Content-Type: application/json
```

Запрос:

```json
{
  "inn": "7700000000"
}
```

Backend ищет уже сохранённую компанию или запрашивает её через `CompanyProvider`. Сейчас подключён `DemoCompanyProvider`; он возвращает явно синтетическую запись. Ответ `200 OK` содержит данные компании и `data_source: "DEMO"`.

Ошибки:

- `401 Unauthorized` — токен отсутствует или недействителен;
- `409 Conflict` — у пользователя уже привязана другая компания;
- `422 Unprocessable Entity` — ИНН содержит не 10 или 12 цифр;
- `502 Bad Gateway` — провайдер компании недоступен или вернул данные с другим ИНН.

### Данные компании

```http
GET /api/v1/company
Authorization: Bearer <access_token>
```

Ответ `200 OK`:

```json
{
  "id": "00000000-0000-0000-0000-000000000001",
  "name": "Демо-компания 7700000000",
  "inn": "7700000000",
  "ogrn": null,
  "registration_date": "2019-01-01",
  "status": "ACTIVE",
  "director_name": null,
  "okved": null,
  "data_source": "DEMO"
}
```

Ошибки:

- `401 Unauthorized` — токен отсутствует или недействителен;
- `404 Not Found` — компания пользователя не найдена.

### Финансовые данные

Получение финансовых показателей. Если запись ещё не создана, Backend получает синтетические данные через `FinancialProvider`, сохраняет их в PostgreSQL и возвращает с `source: "DEMO"`. Повторные запросы читают сохранённую запись.

```http
GET /api/v1/company/financials
Authorization: Bearer <access_token>
```

Ответ `200 OK`:

```json
{
  "revenue_annual": 12500000.00,
  "profit_annual": 2100000.00,
  "expenses_annual": 10400000.00,
  "employees": 8,
  "current_debt": 800000.00,
  "updated_at": "2026-01-15T10:30:00Z",
  "source": "DEMO"
}
```

Частичное обновление показателей перед созданием заявки. В запрос включаются только изменяемые поля:

```http
PATCH /api/v1/company/financials
Authorization: Bearer <access_token>
Content-Type: application/json
```

Запрос может содержать только изменяемые поля:

```json
{
  "revenue_annual": 13000000.00,
  "profit_annual": 2300000.00,
  "expenses_annual": 10700000.00,
  "employees": 9,
  "current_debt": 750000.00
}
```

Ответ `200 OK` возвращает полный объект. Обновляются `updated_at` и `source: "USER_VERIFIED"`.

Ограничения:

- денежные значения не могут быть отрицательными;
- `profit_annual` может быть отрицательным, если компания убыточна;
- число сотрудников не может быть отрицательным;
- пустой запрос, `null` вместо значения и неизвестные поля отклоняются;
- `422 Unprocessable Entity` — ошибка валидации данных.

### Кредитная история

```http
GET /api/v1/company/credit-history
Authorization: Bearer ***
```

Если агрегат ещё не сохранён, Backend запрашивает `CreditHistoryProvider`, сохраняет результат и возвращает его. Сейчас используется `DemoCreditHistoryProvider`; это синтетический агрегат, не реальные данные БКИ.

Ответ `200 OK`:

```json
{
  "active_credits": 2,
  "closed_credits": 5,
  "overdue_count": 0,
  "overdue_amount": 0.00,
  "updated_at": "2026-01-15T10:30:00Z",
  "source": "DEMO"
}
```

## Кредитные продукты

Каталог можно просматривать без авторизации. Все условия ниже синтетические и предназначены только для демонстрации (`data_source: "DEMO"`), это не реальные предложения банков.

### Список активных продуктов

```http
GET /api/v1/credit-products
```

Ответ `200 OK` содержит активные продукты, отсортированные по названию:

```json
[
  {
    "id": "00000000-0000-0000-0000-000000000101",
    "name": "Оборотный кредит",
    "description": "Синтетический demo-продукт для пополнения оборотных средств.",
    "min_amount": 100000.00,
    "max_amount": 5000000.00,
    "min_term_months": 6,
    "max_term_months": 36,
    "interest_rate": 18.90,
    "is_active": true,
    "data_source": "DEMO"
  }
]
```

### Карточка продукта

```http
GET /api/v1/credit-products/{product_id}
```

Ответ `200 OK` возвращает продукт в том же формате; для неизвестного или неактивного ID возвращается `404 Not Found`.

## Заявки — черновики

Все endpoints заявок требуют Bearer JWT и работают только с заявками текущего пользователя. Для создания нужна привязанная компания и активный продукт.

### Создать черновик

```http
POST /api/v1/applications
Authorization: Bearer ***
Content-Type: application/json
```

Запрос:

```json
{
  "product_id": "00000000-0000-0000-0000-000000000101",
  "requested_amount": "100000.00",
  "term_months": 6,
  "purpose": "Пополнение оборотных средств"
}
```

Сумма принимается с точностью до двух знаков после запятой. Она и срок должны попадать в диапазоны активного продукта. Цель — непустой текст длиной до 500 символов. Ответ `201 Created` содержит заявку со статусом `DRAFT`; сумма сериализуется строкой, чтобы не терять точность.

```json
{
  "id": "00000000-0000-0000-0000-000000000201",
  "company_id": "00000000-0000-0000-0000-000000000001",
  "product_id": "00000000-0000-0000-0000-000000000101",
  "requested_amount": "100000.00",
  "term_months": 6,
  "purpose": "Пополнение оборотных средств",
  "status": "DRAFT",
  "created_at": "2026-01-15T10:30:00Z",
  "updated_at": "2026-01-15T10:30:00Z"
}
```

### Список заявок

```http
GET /api/v1/applications
Authorization: Bearer ***
```

Ответ `200 OK` — массив заявок текущего пользователя, сначала новые.

### Получить заявку

```http
GET /api/v1/applications/{application_id}
Authorization: Bearer ***
```

Ответ `200 OK` содержит объект заявки в том же формате, что и создание. Чужая или неизвестная заявка возвращает `404 Not Found`.

### Изменить черновик

```http
PATCH /api/v1/applications/{application_id}
Authorization: Bearer ***
Content-Type: application/json
```

Можно передавать любое непустое подмножество `product_id`, `requested_amount`, `term_months`, `purpose`. Повторно проверяются продукт и диапазоны суммы/срока. Пустой запрос, `null`, неизвестные поля и некорректные значения возвращают `422 Unprocessable Entity`. Редактировать можно только заявку со статусом `DRAFT`; для иных статусов будет `409 Conflict`. Менять статус через PATCH нельзя.

### Отправить заявку

```http
POST /api/v1/applications/{application_id}/submit
Authorization: Bearer ***
```

Ответ `200 OK` возвращает заявку после проверок, подготовки данных и вызова `ml.facade.score_and_explain`. Backend передаёт фасаду признаки из данных заявки и сохраняет неизменяемый snapshot версии `2`: входные данные, источники и временные метки плюс `risk_score`, `risk_level`, `top_factors` и `ai_advice`. Вызов синхронный, но выполняется вне async event loop. История переходов заканчивается на `SCORING`; последнее событие `RISK_ASSESSMENT_COMPLETED` содержит краткую оценку и источник AI/fallback.

Запрос идемпотентен: повторная отправка заявки со snapshot не создаёт новый snapshot, не вызывает скоринг повторно и не добавляет события. `SCORING` означает, что оценка риска сохранена и заявка ждёт решения Backend. Поле `decision` из результата ML намеренно игнорируется: окончательное решение по бизнес-правилам ещё не реализовано.

Если provider недоступен или фасад не вернул валидную оценку, endpoint возвращает `502 Bad Gateway`; заявка остаётся `DRAFT`, snapshot и переходы не сохраняются. Недоступность Ollama сама по себе обрабатывается внутри фасада с `Fallback_Rules`.

### История заявки

```http
GET /api/v1/applications/{application_id}/history
Authorization: Bearer ***
```

Ответ `200 OK` — упорядоченные по `sequence` события со статусами до/после, типом события, временем и участником (`USER` или `SYSTEM`). Чужая или неизвестная заявка возвращает `404 Not Found`.

Ошибки создания, изменения и отправки:

- `401 Unauthorized` — отсутствует или недействителен JWT;
- `404 Not Found` — продукт не существует/неактивен или заявка недоступна;
- `409 Conflict` — компания не привязана либо заявка уже не черновик;
- `422 Unprocessable Entity` — поля запроса или условия продукта не прошли проверку;
- `502 Bad Gateway` — финансовый provider, provider кредитной истории или сам скоринговый фасад недоступен/вернул невалидный результат.

## Текущий статус реализации

Реализованы health-check, регистрация пользователя без компании, login, получение текущего пользователя по JWT, привязка и просмотр компании через `CompanyProvider`, GET/PATCH финансов через `FinancialProvider`, просмотр кредитной истории через `CreditHistoryProvider`, каталог demo-продуктов, заявки со snapshot версии 2 и историей событий, отдельный endpoint скоринга компании и вызов ML-фасада при отправке заявки. Финансовые показатели после пользовательского редактирования маркируются `USER_VERIFIED`. Финальное решение Backend, предложение и подтверждение предложения ещё не реализованы.

## Скоринг и LLM-рекомендация (dev)

`POST /api/v1/company/score` с JWT: `{ "loan_amount": 1000000, "user_query": "Нужен кредит на оборудование" }`. Компания берётся из аккаунта, финансовые признаки рассчитываются на сервере. Полный контракт, формулы, источники AI/Fallback_Rules и ограничения: [ml.md](ml.md).

### Параметры и ошибки скоринга

| Поле | Условие |
| --- | --- |
| `loan_amount` | Обязательно; конечное число > 0 и <= 999999999999 |
| `user_query` | Необязательная строка до 500 символов или null; пустой/отсутствующий запрос заменяется стандартным запросом анализа |

Неизвестные поля запрещены. Клиент не передаёт company_id или готовые признаки: компания и показатели выбираются на сервере для текущего пользователя.

| HTTP | Причина |
| --- | --- |
| 200 | Скоринг выполнен; `ai_advice.source` показывает AI либо Fallback_Rules |
| 401 | JWT отсутствует, недействителен или пользователь не найден |
| 404 | Компания не привязана или не найдена |
| 422 | Невалидный запрос, отсутствующая/будущая дата регистрации, выручка <= 0 |
| 502 | Ошибка получения финансов/кредитной истории через соответствующий provider |
| 409 | Не удалось сохранить данные provider при конфликте |

Ошибка Ollama или невалидный JSON модели обрабатывается запасными правилами и возвращается с HTTP 200 и `source: Fallback_Rules`. Численный риск при этом по-прежнему рассчитывается по правилам. Пример ответа и ручной сценарий: [ML](ml.md).
